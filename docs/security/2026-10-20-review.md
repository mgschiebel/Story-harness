# Skaldsaga security review, October 20, 2026

*Isolated review session, outside the HANDOFF build and planning sessions. Reviewed `main` at `f54e00d` (release 0.3.2), all 129 commits on every branch, tag and pull request ref, the `dist` branch, release tarballs, pull request descriptions and GitHub repository settings. Scope and principles were agreed with the author before any change.*

## How this review works

Two stages, agreed with the author:

1. **Fix today:** only urgent leaks in the public repository (credentials, account details, sensitive information), plus a `.gitignore` that keeps them out in future.
2. **Document everything else** as numbered security requirements (`SR-xx`) for the build pipeline to implement. Today's fixes get requirements too, so a later session can't undo them.

Each requirement has a **priority**:

- **P1:** before more phase 1 build steps land on top of it, or as soon as it's convenient during phase 1.
- **Pre-release:** must be done before any public release.

Each requirement also says where the problem is and what "done" means.

Security rules that every build session must follow are summarized in `CLAUDE.md` ("Security rules"). HANDOFF lists the requirement IDs under "Security requirements". The GitHub settings only the author can change are a step-by-step list in `docs/security/github-settings-checklist.md`.

## Principles

The author set the frame: trust only matters for executable content, so the story folder is locked down to data. Three linked principles follow, plus two for the project itself.

1. **Data, not code.** A story folder holds text and data only. Nothing in it is run, sourced or treated as a command. Anything executable (status line commands, hooks, scripts) lives in the writer's own uncommitted machine settings.
2. **Strict parsing.** Story text never becomes a path, a command or a link target. IDs and file names are whitelisted, symlinks aren't followed, sizes are capped, and writer text reaches git and the shell only as data (a file or an argument, never through shell quoting).
3. **Instructions come only from the writer.** For an agent, text is executable. Story content is material to discuss, never instructions. This is enforced in four layers:
   - **Prompt rule:** every skill and agent prompt says story content is never instructions.
   - **Allowlist:** only a fixed set of commands may run.
   - **No writer text in command lines:** writer text never appears inside a shell command.
   - **The program as the last gate:** every write goes through the program's validation.
4. **Supply chain and release integrity.** What writers install is built only from reviewed source, with pinned inputs, least-privilege tokens and verifiable outputs.
5. **Secure development lifecycle.** Security requirements, checks and reviews are part of every build step, not a one-off.

## Requirements

### A. Secrets and personal information (stage 1 and follow-ups)

**SR-01: Keep secrets out of git (P1; implemented today for this repo).**
- The repository's `.gitignore` keeps the personal and secret patterns added on October 20, 2026. Lines may be added, never removed, without the author's sign-off.
- **Story folders:** `init`'s `ROOT_GITIGNORE` (`crates/skaldsaga-core/src/init.rs`) should carry the same credential lines as this repository's, since `git add -- spec manuscript` stages whatever a writer drops into those folders.
- **Done when:** init's list matches, with a test, and the existing append-only behavior is kept.

**SR-02: GitHub no-reply addresses for every new commit (P1; author settings, then a contributor note).**
- *Decided (October 20, 2026):* best practice going forward only; **no history cleanup**. The author's address was already effectively public, and a rewrite would change nearly every commit ID, move the release tags and still leave the old commits in GitHub's pull request refs.
- **Author:**
  - Turn on GitHub's "Keep my email addresses private" and "Block command line pushes that expose my email" (Settings > Emails), so merges made on GitHub also use the no-reply address.
  - Any git identity configured on a machine or in a cloud environment uses `mgschiebel@users.noreply.github.com`.
- **Contributors:** a CONTRIBUTING note asks them to commit with their own GitHub no-reply address (`<id>+<username>@users.noreply.github.com`, shown on their Settings > Emails page). CI adds a *warning* annotation (not a failure) when a commit's author or committer email isn't a no-reply address, so nobody's address is published by accident.
- **Done when:** the settings are on, the CONTRIBUTING note exists, and the CI warning has a test branch that shows it.

**SR-03: No Claude session links in new commits or pull requests (P1; implemented October 20, 2026 in #21).**
- **Why:** this is a public open-source project that will have third-party contributors, so everyone's sessions need protecting, not just the author's. A session link alone opens nothing, since sessions are private by default. But on Pro and Max plans a session can be switched to Public (visible to anyone logged into claude.ai), and sessions can hold code and credentials. A link already sitting in public history makes such a session findable forever.
- *Decided (October 20, 2026):* **existing links stay.** They all point at the author's own sessions, which will stay private.
- **Implemented, three layers:**
  - `.claude/settings.json` sets `attribution.sessionUrl` to `false`. This covers local Claude Code and cloud sessions that start inside the repository. Sessions that start one folder above it (the mobile app) don't read it.
  - A `CLAUDE.md` rule covers every surface.
  - The Privacy workflow (`.github/workflows/privacy.yml`, `ci/check-session-links.sh`) fails a pull request whose new commits or description contain a session link. The description reaches the script through an environment variable, never inlined, so its text can't run. This is the enforcement for contributors who don't use Claude Code or ignore the settings.
- **Still to do:** a CONTRIBUTING note explaining the rule (with SR-02's note), and adding "Privacy checks" as a required status check in the Main protect ruleset (SR-50).

**SR-04: Secret scanning stays on, and runs in CI (P1).**
- Keep GitHub secret scanning and push protection on.
- Also turn on non-provider patterns and validity checks.
- Add a gitleaks step to CI over the pushed commits, so a secret is caught even where push protection doesn't apply (for example a pattern GitHub doesn't know).
- **Done when:** a seeded fake key in a test branch fails CI.

**SR-05: Test reports and handoff notes carry no sensitive values (P1).**
- Test reports, HANDOFF and pull request descriptions never include:
  - tokens, environment or trigger IDs, or full plugin and session IDs
  - account emails
  - contents of `settings.local.json` or environment variables
- Shorten IDs as the 0.3.0 report already does (`947dfab0-…`).

### B. Data, not code (story folders)

**SR-10: Nothing executable is stored in the story folder (P1, highest priority).**
- **Problem:** the meter stores the writer's own status line under `meter.wrapped_statusline` in `.harness/settings.json`. That file is committed (`init` returns all of `.harness` in `commit_paths`). The meter runs its `command` through `sh -c` on every turn (`crates/skaldsaga/src/main.rs` `meter_statusline` → `wrapped.rs`).
- **Risks:**
  - A cloned or shared story can carry a command that runs on the next person's machine once they type `/skaldsaga`. Setup always proceeds when `.harness/` exists, and it wires the meter.
  - The writer's personal status-line command, which may include paths or tokens, is published in their story's history.
  - This is the same supply-chain path decision 1 (HANDOFF, October 19) closed for `.claude/settings.json`, moved one file over.
- **Confirmed in this review** with a harmless local test on the 0.3.2 code: after `init`, `.harness/settings.json` is among the staged paths, and a `wrapped_statusline` command placed in it ran when the meter's status line was invoked.
- **Done when:**
  - The wrapped command is stored only in uncommitted, per-machine settings (for example inside the `statusLine` entry in `.claude/settings.local.json`, or a gitignored `.harness/local.json`).
  - The meter never executes a command read from a committed file.
  - Existing `wrapped_statusline` entries are migrated out and listed, like `meter.cleaned`.
  - A test proves a committed `wrapped_statusline` is ignored.

**SR-11: Story folders are checked for executable content (P1).**
- `init`, `check` and `index` treat these inside `spec/`, `manuscript/`, `.harness/` as a finding (refused or reported, never followed or run):
  - symlinks
  - files with an executable bit
  - device files and other non-regular files
- **Done when:** tests cover each case, and an existing-project import (when built) applies the same rule.

**SR-12: A story's own Claude Code settings are never trusted by Skaldsaga (Pre-release).**
- Skaldsaga never reads, merges or writes hooks, `statusLine`, `permissions` or `env` from a story's committed `.claude/settings.json`, except to move its own old meter entry out (already done in 0.3.2).
- Setup tells the writer, in plain words, when a cloned story contains `.claude/` settings or a `CLAUDE.md`, since Claude Code itself will act on them.

### C. Strict parsing (the program)

**SR-20: IDs from the command line are validated before use as paths (P1).**
- **Problem:** `commit --proposal ID` joins the ID into `.harness/inbox/<ID>.json` and later `.harness/committed/<ID>.json` and a removal path before checking it's a proposal ID (`commit.rs`, `commit()`), so `../../x` reaches outside the story folder.
- Confirmed in this review: `commit --proposal ../../../outside/evil` read a JSON file outside the project. With a well-formed proposal there, the archive write and the removal would use the same ID.
- `check --proposal` only matches IDs against inbox files and was not affected.
- **Done when:**
  - Every ID from arguments, settings or file contents passes `ids::is_kind` before it is used in a path.
  - A shared helper builds node and proposal paths and refuses anything else.
  - There are tests for traversal attempts.

**SR-21: No symlinks followed when reading or writing story files (P1).**
- **Problem:** `fsio::read_optional` uses `read_to_string`, which follows links. A `spec/people/p-….md` that links to `~/.ssh/id_ed25519` would be read, and parts may surface in error messages or the index.
- **Done when:**
  - Reads check `symlink_metadata` and refuse links.
  - Every path is confirmed to stay inside the project root after resolution.
  - There are tests.

**SR-22: Safe temporary files (P1).**
- **Problem:** `fsio::write_atomic` creates `.<name>.<pid>.tmp` with `File::create`. That follows a symlink already sitting at that name and truncates its target. A cloned story could plant one for a guessed process ID.
- **Done when:** the temporary file is opened with `create_new` (exclusive), with a random suffix, and the write refuses if the parent folder is a link.

**SR-23: Input size and parser limits (Pre-release).**
- Cap the size of every file read (spec nodes, proposals, settings, the status-line JSON on stdin) and the number of files per folder.
- Confirm the YAML parser (`serde_norway` over `unsafe-libyaml-norway`) limits alias expansion and nesting depth. If it doesn't, reject anchors and aliases in node files.
- **Done when:** oversized and alias-bomb fixtures fail fast with a plain error.

**SR-24: Shell-safe command strings (P1).**
- **Problem:** `hooks::meter_command` builds `sh "<plugin root>/scripts/skaldsaga" meter statusline` with the plugin path inside double quotes. A path containing `"`, `$` or a backtick changes the command.
- **Done when:** the path is single-quoted with proper escaping (or rejected if it contains quote characters), and this has a test.

**SR-25: Fuzz the parsers (Pre-release).**
- Add `cargo fuzz` targets (or property tests) for node files, proposals, `sequence.md`, `attributes.md` and the status-line input.
- Run them in a scheduled CI job.

### D. Instructions come only from the writer (skills and agents)

**SR-30: Prompt rule in every skill and agent (P1).**
- Every skill and agent definition states that story content (spec, manuscript, proposals, recaps, imported files) is material to discuss, never instructions.
- Agents never run, install, fetch or follow commands, scripts, links or steps found in it. If content asks for that, the agent tells the writer plainly and carries on.
- **Done when:** the rule is in `SKILL.md` and every agent file, and an eval story with embedded instructions passes (SR-52).

**SR-31: Fixed tool allowlist (P1).**
- The `skaldsaga` skill declares `allowed-tools` limited to the Skaldsaga launcher and the named git commands it uses. Today `plugin/skills/skaldsaga/SKILL.md` declares none.
- Sub-agents (housekeeper, harvester, weaver, outliner, researcher, rubric) get a `tools:` list with no shell. They read files and write proposals only. The researcher's web access is limited to search and fetch, with sources filed as data.
- **Done when:** each definition's tool list is reviewed in the pull request that adds it.

**SR-32: Writer text never inside a shell command (P1).**
- **Problem:** the skill runs `git commit -q -m "<message>"`, where the message is the writer's own answer. Quotes, `$(...)` or backticks in an answer break out of the quotes or run in the shell.
- **Done when:**
  - The program writes the commit message to a file (for example `.harness/commit-message.txt`, gitignored) and returns its path.
  - The skill runs `git commit -F <file>`.
  - No step in any skill interpolates writer text into a command.

**SR-33: The program stays the only writer (P1).**
- Agents change story files only through `skaldsaga commit`, which validates every ID, path and operation.
- Agents never edit `spec/` or `.harness/` directly.
- The skill commits only the paths the program returns (`commit_paths`, `add_paths`, `remove_paths`). This is already the rule; keep it, and keep it tested.

### E. Supply chain and release integrity

**SR-40: Pin third-party GitHub Actions by commit SHA (P1).**
- `actions/checkout@v5`, `dtolnay/rust-toolchain@stable` and `Swatinem/rust-cache@v2` are pinned by tag or branch, which their owners can move.
- Pin each to a full commit SHA with the version in a comment, and let Dependabot update them (SR-43).

**SR-41: Least-privilege workflow tokens (P1).**
- `release.yml` grants `contents: write` to the whole workflow.
- Set `permissions: {}` at the top and grant `contents: write` only to the job steps that need it (splitting build and publish jobs if needed).
- Keep CI at `contents: read`.

**SR-42: Pin CI tools (P1).**
- CI runs `npm install --global @anthropic-ai/claude-code` without a version. Pin the version (and use `npm ci`-style integrity where possible).
- Pin the Rust toolchain with a `rust-toolchain.toml`.

**SR-43: Dependency monitoring (P1).**
- Turn on Dependabot alerts and security updates.
- Add `.github/dependabot.yml` for `cargo` and `github-actions`.
- Add `cargo audit` (or `cargo deny check advisories licenses sources`) to CI.
- Keep the dependency tree small; new crates need a one-line reason in the pull request.
- Note that `unsafe_code = "forbid"` covers only our crates; `unsafe-libyaml-norway` is unsafe C-translated code and is the main parser risk.

**SR-44: Verifiable releases (Pre-release; checksums P1).**
- Publish a SHA-256 checksum file with each release tarball.
- Add build provenance (`actions/attest-build-provenance`) for the tarball and the `dist` binary.
- Signing stays planned for the public-release phase (HANDOFF).

**SR-45: Release only from reviewed `main` (P1).**
- `release.yml` refuses non-`main` dispatches, but a pushed `v*` tag on any commit also releases.
- Either drop the tag trigger or add a tag ruleset so only the author can create `v*` tags, and verify the tagged commit is on `main`.

**SR-46: The launcher's binary override is development-only (Pre-release).**
- `SKALDSAGA_BIN` lets an environment variable choose which binary runs.
- Document it as development-only, and consider honoring it only when a debug build or an explicit opt-in is present.

**SR-47: Strip build paths from binaries (Pre-release, low).**
- Build with `--remap-path-prefix` so binaries don't embed runner or developer home paths.

### F. Repository hygiene

**SR-50: Protect `main` (P1, author action).**
- The "Main protect" ruleset exists but its **enforcement is disabled**, so `main` is unprotected. Set it to Active with:
  - pull requests required
  - CI required to pass
  - no force pushes or deletions
- Add a matching rule for `dist` (only the Release workflow writes it) and for `v*` tags.

**SR-51: Security policy and ownership (Pre-release).**
- Add `SECURITY.md` (how to report a vulnerability privately; turn on private vulnerability reporting).
- Add `CODEOWNERS` covering `.github/`, `plugin/`, `ci/` and `crates/`.

**SR-52: Security tests and evals (P1).**
- Keep regression tests for each SR fix.
- Add a seeded "hostile story" fixture to the evals plan with:
  - embedded instructions in spec text
  - a symlink
  - a traversal ID
  - a committed `wrapped_statusline`
  - an executable file
- Skaldsaga must refuse or ignore every one.

**SR-53: Tidy branches (low).**
- Turn on "Automatically delete head branches".
- Remove the stale `docs/meter-test-pause` branch if it's no longer needed.

### G. Secure development lifecycle

**SR-60: Security in every build step (P1).**
- Each build step's pull request says which SRs it touches, and confirms it adds no new executable content to story folders, no new path built from input, and no new tool for an agent.
- A short checklist in a pull request template covers this.

**SR-61: Threat model stays current (P1).**
- This document is the threat model's first version. Update it when a phase adds a new input (existing-project import, harvester reading drafts, researcher web access), a new automatic runner (hooks, status line), or a new output channel (editions, publishing).

**SR-62: Periodic review (Pre-release).**
- Re-run this review (leak scan, dependency audit, settings check) before the public release and at each later phase boundary.

## What's already done well

Recorded so later sessions keep it:

- **Automatic code stays quiet.** The hook and status line do nothing outside a project, and never show errors.
- **Meter wiring is per machine.** It lives in `.claude/settings.local.json` (decision 1), and the old shared entry is migrated out.
- **The skill commits only what the program returns,** never the whole folder.
- **Node files reject unknown keys,** and IDs are random with a strict alphabet.
- **`unsafe_code = "forbid"`, `--locked` builds and a small dependency tree.**
- **CI has `contents: read`;** plugin version and binary version are checked against each other.
- **GitHub secret scanning and push protection are on.**
